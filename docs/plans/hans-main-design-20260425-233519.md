## Problem Statement

Build a portfolio-grade backend service that pulls BTC/ETH prices from multiple
exchanges, normalizes the data (symbols, decimals, fee structures), stores ticks
in Postgres (TimescaleDB hypertables), and exposes a single REST endpoint
returning a volume-weighted average price along with confidence and rejection
metadata. The artifact's job is to demonstrate senior-engineer judgment to a
hiring manager skimming the repo for 90 seconds.

## What Makes This Cool

The differentiator is not the code — it's the README and the test suite.
Specifically: "VWAP is harder than it looks." Clock skew, stale-data
detection, outlier rejection, and weighting decisions each become a section.
The response shape (`{vwap, confidence, sources_used, sources_rejected, reasons}`)
makes the project's thesis visible in the first line of the README. The
"Things That Will Lie To You" section runs before the architecture diagram.
A captured flash-crash example shows the anomaly layer in action.

## Stack Tiers

The design separates **what's load-bearing** from **what's a defensible
choice**. The README mirrors this — a reviewer should be able to swap any
"recommended" component for the listed alternative without changing the
architecture or breaking the correctness thesis.

|---|---|---|---|
| Web framework | Rails 7.1+ | Rails 7.1 (full, not API-only — needs views) | Sinatra (loses Hotwire/Sidekiq integration) |
| Language | Ruby 3.3+ | Ruby 3.3+ | — |
| Database | Postgres 15+ | Postgres + TimescaleDB extension | Vanilla Postgres + `time_bucket()`-equivalent SQL helpers |
| Frontend / JS | Some JS | Hotwire (Turbo Streams + Stimulus) | Inertia + React (Hans's daily driver), or plain Stimulus |

| Tests | (any) | RSpec + WebMock + VCR | Minitest + WebMock + VCR |
| Linting | (any) | RuboCop (rubocop-rails) + Brakeman | Standard.rb |
| Local dev | docker-compose | docker-compose with Postgres+Timescale + Redis + Rails + Sidekiq | `bin/setup` + manual service start (Postgres/Redis via Homebrew) |

The "core" column is the load-bearing minimum: pull any of those out and
the project doesn't make sense. Everything else is a choice you can defend
in the README and swap if you ever revisit. This tiered structure is itself
a signal — it tells the reviewer "I know which decisions matter and which
are taste."
- Tests must run offline against recorded fixtures — no flaky live-API tests in CI.
- **Pair scope, v1: BTC-USD only.** ETH-USD added once the pipeline is proven —
  it costs nothing once the kernel is generic.
- **USD vs USDT policy, v1:** treat `USD` and `USDT` as the same quote
  currency for the canonical pair. Binance has no native `BTC/USD` (only
  `BTC/USDT`); Coinbase has `BTC-USD`; Kraken has `XBT/USD`. The README
  documents the assumption (USDT depeg risk acknowledged) and the symbol
  mapping table makes it explicit.

## Symbol Mapping (canonical → exchange)

No `ccxt` in Ruby — each adapter handles its own raw-symbol translation.
The mapping is owned by `Aggregator::Sources::<Exchange>` and tested per
adapter.

| Canonical (API) | Binance | Coinbase | Kraken |
|---|---|---|---|
| `BTC-USD` | `BTCUSDT` (ticker endpoint) | `BTC-USD` (product_id) | `XXBTZUSD` (pair) |
| `ETH-USD` (Phase 1.5) | `ETHUSDT` | `ETH-USD` | `XETHZUSD` |

Each adapter's `#fetch` method normalizes the response into
`Aggregator::Tick.new(exchange:, pair:, price:, quote_volume_24h:,
source_ts:)` so downstream code never sees the raw symbol.

## Approaches Considered

### Approach A: Correctness Kernel only
Pure correctness kernel + Rails JSON API + TimescaleDB. Three exchanges
polled at 2s. README leads with failure-modes section. No anomaly layer,
no dashboard.
Effort S, Risk Low. Ships fast. Less differentiated.

### Approach B: Correctness + Anomaly Layer (chosen)
Same kernel as A, plus a second module tracking per-exchange divergence from
consensus over rolling windows. Each tick gets a `divergence_score`. The
`/price` response surfaces rejected sources with reasons. README dedicates a
section to "When 4 exchanges agree and one doesn't, who's right?" with a
captured flash-crash example. Effort M, Risk Low-Med. Ships clean and tells a
richer story.

### Approach C: Real-Time + Replay Harness (lateral)
Skip REST entirely, go straight to WebSocket fan-in (Ruby `async-websocket`
or `faye-websocket-ruby`, hand-rolled per exchange — no ccxt equivalent),
with a record-and-replay CLI that captures live feeds for deterministic
testing. Effort L, Risk Med-High. Violates premise #3. Held for iteration 3.

## Kernel Constants (v1)

These need concrete values, not handwaving. Document in the README.

| Constant | Value | Why |
|---|---|---|
| Polling interval | 2.0s | Fast enough to feel real-time; slow enough to stay under all 3 rate limits with margin |
| Aggregation window (N) | 10s | The endpoint computes the response from ticks ingested in the last 10s. Defines "current price." |
| Staleness SLO (per source) | 10s | A tick whose `source_ts` is older than 10s relative to `Time.now.utc` is rejected. (Same value as window — every tick in window is by definition fresh enough.) |
| MAD baseline | Median of latest one tick per source within the aggregation window | Compute MAD relative to that median. One tick per exchange (the freshest within the window) avoids weighting fast-pollers more. |
| MAD outlier threshold (k) | 5.0 | Reject a tick whose price differs from the cross-source median by > 5 × MAD. Conservative; tunable in config. |
| Min sources for `confidence: "ok"` | 3 | All three healthy. |
| Min sources for `confidence: "degraded"` | 2 | Two healthy. Response includes `sources_rejected` with reasons. |
| Min sources for response | 2 | Below 2, return HTTP 503 with `reason: "insufficient_sources"`. Don't lie. |
| Retry policy | 3 attempts, exponential backoff (250ms, 1s, 4s), then mark source unhealthy for 30s | |
| Clock-anchoring | `Time.now.utc` (wall clock, system NTP-synced) | See "Clock anchoring" below |

**Clock anchoring (resolved):** v1 uses `Time.now.utc` and trusts the
host (your laptop or any Linux VM with `systemd-timesyncd` / `chronyd`) to be NTP-synced.
`Process.clock_gettime(Process::CLOCK_MONOTONIC)` is used only for
*intra-process* elapsed-time measurements (retry backoffs, request
latency). The 10s staleness SLO is generous enough to absorb sub-second
NTP drift. The README documents the assumption and what would force a
switch to per-exchange `serverTime` normalization (answer: a measured
cross-source skew > 1s in practice).

## VWAP Weighting: Honest Definition

**Critical decision** — the reviewer caught this and they're right. REST
polling at 2s samples the ticker; it does not observe per-trade volume. So
the "V" in VWAP needs a defensible source.

- **v1 weight: ticker `quoteVolume` (24h trailing, exposed by all three
  exchanges).** The aggregate is therefore a **consensus price weighted by
  each exchange's recent activity level**. The README must call this out
  honestly: "This is not literal trade-by-trade VWAP. It is a consensus mid
  weighted by 24h `quoteVolume`. See the math section for why this is the
  right choice for a snapshot aggregator. True trade-by-trade VWAP requires
  WebSocket trade streams — see iteration 3."
- **Function name**: `consensus_price()` internally. The endpoint stays
  `/price` and the response field is `vwap` (industry convention) but the
  README math section disambiguates.

This is the kind of explicit tradeoff documentation that reads as senior
judgment rather than as oversight.

## Response Schema (v1)

Endpoint: `GET /price/{pair}` where `{pair}` ∈ {`BTC-USD`}.

**200 OK** (response body):
```json
{
  "pair": "BTC-USD",
  "vwap": "67432.18",
  "confidence": "ok",
  "as_of": "2026-04-25T23:42:00.123Z",
  "window_seconds": 10,
  "sources_used": [
    {"exchange": "binance",  "price": "67430.50", "weight": "0.42", "source_ts": "2026-04-25T23:41:58.910Z"},
    {"exchange": "coinbase", "price": "67434.00", "weight": "0.31", "source_ts": "2026-04-25T23:41:59.020Z"},
    {"exchange": "kraken",   "price": "67432.05", "weight": "0.27", "source_ts": "2026-04-25T23:41:59.450Z"}
  ],
  "sources_rejected": []
}
```

- `vwap`, `price`, `weight` are decimal strings (never JSON floats — never
  send currency through IEEE-754).
- `confidence` ∈ {`"ok"`, `"degraded_outlier"`, `"degraded_unreachable"`}.
  Two distinct degraded buckets: outlier rejection vs unreachable source —
  these are different failure modes and the README's failure-modes section
  explains why they get different labels.
- `weight` is each source's share of total `quoteVolume` across used sources
  (sums to 1.0 ± rounding).

**`sources_rejected` entries:**
```json
{"exchange": "okx", "reason": "stale", "detail": "source_ts age 14.2s > SLO 10s"}
{"exchange": "bybit", "reason": "outlier", "detail": "price 65120.00 vs median 67432.05, MAD 12.1, k=387.5"}
{"exchange": "kraken", "reason": "unreachable", "detail": "3 retries failed; circuit open for 22s"}
```

**503 Service Unavailable** (insufficient sources):
```json
{
  "pair": "BTC-USD",
  "error": "insufficient_sources",
  "sources_used": 1,
  "sources_required": 2,
  "sources_rejected": [...]
}
```

## Recommended Approach

**Approach B**, shipped in two phases.

**Phase 1 (v1, 2-3 weeks of evenings):**
- `spec/aggregator/replay_spec.rb` is the first file. Three captured JSON
  payloads under `spec/fixtures/exchanges/`: one stale (12s old), one
  outlier ($0.01 print), one clean. RSpec test asserts the kernel rejects
  the bad two and returns the consensus price from the third with
  `confidence: "degraded_outlier"` and a structured rejection list. No
  Rails, no DB, no HTTP — pure Ruby objects under test.

  **Required edge-case tests (silent-failure prevention):**

  1. **`spec/requests/api/v1/prices_serialization_spec.rb`** — assert
     `vwap`, `price`, and `weight` fields in the JSON response are
     decimal STRINGS, not JSON numbers. Currency through IEEE-754 is a
     real bug. Use `parsed_response["vwap"].is_a?(String)`. **Mark
     CRITICAL.**
  2. **`spec/aggregator/core_mad_zero_spec.rb`** — when all 3 sources
     report identical prices, MAD = 0 and `(price - median) / MAD`
     would raise. Test asserts the kernel handles MAD = 0 gracefully
     (no rejections, all sources used). **Mark CRITICAL.**
  3. **`spec/aggregator/core_zero_volume_spec.rb`** — when one source
     has `quote_volume_24h = 0` (rare but happens during exchange
     maintenance windows), the weighting must not divide by zero.
     Either drop the source (preferred, treat as unreachable) or
     fall back to equal weighting. Test the chosen behavior.
     **Mark CRITICAL.**
  4. **`spec/aggregator/core_staleness_boundary_spec.rb`** — tick at
     exactly 10.000s old: kept or dropped? Pick one (recommend "older
     than" so 10.0s is dropped) and test it. Off-by-one at the SLO
     boundary is the kind of thing you only catch in production.
     **Mark CRITICAL.**
  5. **`spec/aggregator/sources/binance_rate_limit_spec.rb`** — when
     Binance returns 429 with `Retry-After: 5`, the adapter must
     honor the header (sleep 5s, not 250ms exponential backoff).
     WebMock the 429 response. Without this, sustained polling will
     get the IP banned for 24h. **Mark CRITICAL.**

  All 5 are unit-style specs against the kernel or adapters — no Rails,
  no live network. Fast (<100ms each).
- Correctness kernel (`app/aggregator/core.rb` — POROs, not ActiveRecord):
  wall-clock staleness checks, MAD-based outlier rejection, 24h
  `quote_volume` weighting (see "VWAP Weighting" above). `Aggregator::Tick`
  value object, `Aggregator::Aggregate` value object, `Aggregator::Core.compute(ticks:)`
  method. ~200 lines of Ruby. **Two `Tick` types intentionally:**
  - `Aggregator::Tick` (PORO, in `app/aggregator/tick.rb`) is the
    value object the kernel operates on. Pure Ruby, no Rails, no DB.
    Used by `Aggregator::Core.compute`, by replay specs, by adapters
    when normalizing API responses.
  - `Tick` (ActiveRecord, in `app/models/tick.rb`) is the storage
    record. Backed by the `ticks` hypertable. Has a `Tick#to_value`
    method returning an `Aggregator::Tick`, and a class method
    `Tick.recent_values(window: 10.seconds)` that returns an array of
    `Aggregator::Tick`s for the kernel to consume.
  - The boundary: anything in `app/aggregator/` is pure Ruby. Anything
    in `app/models/` or `app/controllers/` knows about Rails. The
    converter is the one bridge.
- **Inline ASCII diagram in `app/aggregator/core.rb`** at the top of
  the file (in a comment), showing the compute flow:

```
# Aggregator::Core.compute
# ─────────────────────────
# Input: array of Aggregator::Tick (from Tick.recent_values(window: 10s))
#
#   ticks ──→ filter_stale ──→ filter_outliers ──→ weight_and_sum
#               (drop ticks      (drop ticks         (quote_volume_24h
#                older than       beyond k×MAD        weighted; sum to
#                10s SLO)         from median)        Aggregate)
#
# Output: Aggregator::Aggregate { vwap, confidence, sources_used,
#                                 sources_rejected, as_of }
#
# Confidence ladder:
#   3 sources used       → "ok"
#   2 sources, 1 outlier → "degraded_outlier"
#   2 sources, 1 unreach → "degraded_unreachable"
#   <2 sources           → raise InsufficientSources (controller → 503)
```

This diagram is the kernel's contract. Update it whenever the flow
changes — stale diagrams are worse than no diagrams.
- Three Faraday-based exchange clients (`app/aggregator/sources/binance.rb`,
  `coinbase.rb`, `kraken.rb`). Each uses `faraday` + `faraday-retry` for
  HTTP, exponential backoff per the kernel constants table. Each adapter
  has its own RSpec contract test with VCR-recorded fixtures.
- Polling architecture (sub-minute, so **not** `sidekiq-cron` — its minimum
  granularity is 1 minute). Two options, pick one:
  - **(Chosen) Self-rescheduling Sidekiq jobs.** Each `ExchangePollJob`
    fetches → normalizes → writes a tick row → triggers an
    `AggregateBroadcastJob` → enqueues itself via `perform_in(2.seconds)`
    at the end. **Initial scheduling happens in `config/initializers/poller.rb`
    gated on `Sidekiq.server?`** — so only the Sidekiq process boots the
    chain (not the web process, not the rails console, not test runs).
    Without this gate every Rails process would fire its own polling
    chain, blowing through Binance's rate budget within minutes. The
    initializer is a one-liner per exchange:
    `ExchangePollJob.perform_async("binance") if Sidekiq.server? && !ExchangePollJob.in_flight?("binance")`.
    Crash-resilient: Sidekiq retry handles transient failures, and a
    supervisor job (`PollerSupervisorJob`, runs every minute via
    `sidekiq-cron`) re-enqueues any exchange whose last tick is > 30s old.
  - **(Alt) `sidekiq-scheduler` with `every: 2s`.** Simpler but less
    resilient and the sub-2s drift compounds.
- The job pipeline: fetch → normalize → write tick. **Broadcasting is
  decoupled from polling** to avoid out-of-order Turbo Stream renders.
  A separate self-rescheduling `BroadcastTickJob` fires every 1s,
  reads the latest consensus from the kernel, and pushes one Turbo
  Stream update via Action Cable (Redis adapter — see `cable.yml`
  config below). Pollers never broadcast directly. Three-poll-rate is
  decoupled from one-broadcast-rate, eliminating the race where
  Binance's older snapshot overwrites Coinbase's newer one in the
  dashboard.

```
PIPELINE (decoupled write/broadcast)
─────────────────────────────────────
ExchangePollJob[binance]    every 2s ─┐
ExchangePollJob[coinbase]   every 2s ─┼─→ INSERT INTO ticks
ExchangePollJob[kraken]     every 2s ─┘

BroadcastTickJob            every 1s ──→ Tick.recent_values(10s)
                                      → Aggregator::Core.compute
                                      → Turbo::StreamsChannel.broadcast
                                      → dashboard updates once/sec
```
- Postgres + TimescaleDB schema (Rails migrations):
  - `ticks` hypertable: `(exchange, pair, price NUMERIC(20,8),
    quote_volume_24h NUMERIC(28,8), source_ts, ingested_ts)`. Migration
    uses raw SQL: `execute "CREATE EXTENSION IF NOT EXISTS timescaledb"`
    then `execute "SELECT create_hypertable('ticks', 'ingested_ts', if_not_exists => TRUE)"`.
  - **Composite index:**
    `add_index :ticks, [:exchange, :pair, :ingested_ts], order: { ingested_ts: :desc }, name: 'idx_ticks_lookup'`.
    The hot `/price` query is "latest tick per (exchange, pair) in the
    last 10s." Without this index the query scans recent chunks; with
    it, the query is a backwards-index scan returning at most 3 rows.
    At portfolio-repo volume the perf delta is negligible, but the
    README's "I considered the indexing strategy" sentence is part of
    the senior-engineer signal.
  - **Chunk + retention policy** (Phase 2 — but acknowledge in v1 README):
    `add_retention_policy('ticks', INTERVAL '30 days')` once the table
    has >100k rows. v1 doesn't need it (low volume), but the README's
    "What I didn't build and why" mentions it explicitly.
  - **Local TimescaleDB:** the `docker-compose.yml` pulls
    `timescale/timescaledb-ha:pg16` (or `timescaledb:latest-pg16` for the
    smaller image). No external service, no signup, no cloud account.
    Migration enables the extension on first run. This is the
    local-first answer; Render-Postgres incompatibility no longer
    applies.
  - **If a reviewer doesn't want Docker:** the migration is wrapped in
    `if extension_supported?('timescaledb')` — without the extension,
    the schema falls back to a vanilla Postgres `ticks` table + a
    handful of `time_bucket()`-equivalent SQL helpers in
    `app/aggregator/queries.rb`. Documented in README's "Without Docker"
    quickstart.
  - No `aggregates` table in v1. The endpoint computes on demand from the
    last N=10s of ticks. Persisted aggregates are out of scope until
    there's a use case for backfill/queries.
  - Use `NUMERIC` (not `FLOAT`) for prices — never store currency in
    IEEE-754. Document this in the README.
- Rails routes:
  - `GET /price/:pair` (controller: `Api::V1::PricesController#show`)
    returns the structured JSON response. Skip CSRF
    (`protect_from_forgery with: :null_session` in
    `Api::V1::BaseController`). Open CORS via `rack-cors` for `GET`
    only — the API is read-only and public.
  - `GET /healthz` returns `{status: "ok", db: "ok", redis: "ok",
    sources_healthy: 3}`.
  - `GET /` renders the Hotwire dashboard (see Frontend section below).
- Per-exchange rate-limit budgets (documented in each adapter):
  - Binance: 1200 req/min weight (using `/ticker/24hr` is weight 40 →
    safe at 30/min; we poll at 30/min = 0.5 Hz — wait, we poll at 2s =
    30/min, weight 40 × 30 = 1200/min, exactly the budget). **Reduce
    to 3s polling for Binance specifically** if reviewer prefers
    margin, or use the lighter `/ticker/price` endpoint (weight 1).
  - Coinbase Advanced Trade API: ~30 req/s public budget. 0.5 Hz is
    trivially safe.
  - Kraken: ~1 req/s soft cap on public endpoints. 0.5 Hz is safe.
  - Each adapter's README/docstring records the budget calculation.
- **No Prometheus exposition in v1** — added in Phase 2 alongside anomaly
  metrics, where it actually has something to expose. (`yabeda` + `yabeda-prometheus`
  is the Rails-idiomatic choice when it lands.)
- README v1 (Markdown in repo): opens with the response example, then
  "Three exchanges, because the fourth one was lying on Tuesday," then
  "Why Rails for an aggregator?" (the unconventional-choice defense),
  then Things That Will Lie To You, then math section, then Quickstart,
  then architecture diagram (last), then "What I didn't build and why."
- Distribution: `docker-compose.yml` is the primary path (see Distribution
  Plan below). Reviewer runs `docker compose up` locally. Production deploy
  (`render.yaml`) is a stretch goal, post-v2.

### Anti-slop discipline

Two specific guards against the dashboard becoming "a website with numbers
on it" rather than an instrument:

1. **Chrome bar metadata is real, not decorative.** The values shown
   ("poll 2.0s · window 10s · k=5.0") come from `Aggregator::Constants`
   — a single Ruby module that is the source of truth for these numbers.
   Change `k` there, the chrome bar reflects it. Change the polling
   interval, the chrome bar reflects it. If they ever drift out of sync
   with reality, the dashboard is lying to the reviewer about the
   project's own correctness story. Test in `spec/views/dashboard_spec.rb`:
   "renders constants from `Aggregator::Constants`, not literal strings."
2. **Sparkline shows real data.** It plots actual consensus VWAP over
   the last 60s, sampled once per second, from the same `Tick.recent_values`
   query the consensus uses (just widened to 60s). If the line is flat,
   leave it flat. Faked variance ("smoothed for visual appeal") is a tell
   that makes the rest of the project look uncalibrated. README's "Math"
   section explicitly states the sparkline is real data.



- **Turbo Streams over Action Cable** push the latest aggregate to all
  subscribed clients on a fixed 1s cadence via `BroadcastTickJob`
  (decoupled from polling — see Pipeline diagram in the polling
  section). The job calls
  `Turbo::StreamsChannel.broadcast_replace_to(...)`. Page updates with
  no client-side polling and no JS framework.
- **Stimulus** controllers handle the small amount of client-side state:
  showing a "last update" timer, color-coding sources by health
  (green/yellow/red for ok/degraded_outlier/unreachable), and toggling the
  rejection details panel.
- **Layout**: a single ERB view (`app/views/dashboard/show.html.erb`) with
  three columns: current consensus price (big), per-source breakdown
  (price, weight, status, age), and recent rejections (rolling 60s log).

- **Action Cable config:** `config/cable.yml` uses the Redis adapter in
  production (sharing the same Redis instance as Sidekiq via

  not triggered by pollers) calls
  `Turbo::StreamsChannel.broadcast_replace_to(:price_BTC_USD, target:
